### What does "120 cases" mean?

The 120 cases are a controlled experimental test set, not simply 120 generated scenarios. Each case is an input specification that defines the required role, stage, age group, channel, variant, difficulty condition, and expected cybersecurity behavior.

The design is:

```text
30 base groups = 3 channels x 2 variants x 5 roles
90 anchor cases = 30 base groups x 3 difficulty anchors
30 balanced repetitions = 30 base groups x 1 additional rotating case
Total = 120 cases
```

The same 120 case IDs are used for every LLM and every generation method. This creates a matched comparison.

### Could the scenarios generated by each method be totally different?

Yes. The text can be different. The experiment does not require each method to produce identical wording. It requires each method to satisfy the same input case. Therefore, the comparison is controlled by the case specification, not by the surface text.

Example:

```text
Case PSQ-SCO-120-017 might require:
role = FINANCE
stage = INTERMEDIATE_DEVELOPING
age group = A2235
channel = email
variant = fake
difficulty condition = medium_applied
```

Each method may generate a different email scenario, but all outputs are checked against the same required controls.

### Is prompt+RAG vector RAG?

Yes, when ChromaDB is available. The project uses ChromaDB PersistentClient with cosine HNSW retrieval for the quality-profile index. The evaluator reports the vector database, index path, corpus size, source files, preprocessing, chunking, and retrieval settings.

If ChromaDB is unavailable, the generation engine can fall back to JSONL lexical retrieval. That fallback status must be reported if used.

### Are the same documents used?

For retrieval-enabled conditions, yes. `prompt_rag`, `ontology_prompt_rag`, and `ontology_text_rag` use the same `PSQ_RAG_PROFILE=quality` source corpus unless a run explicitly overrides the environment. `prompt_only` intentionally does not retrieve documents.

### Was the input labeled by attack type and difficulty?

The case-set generator deterministically assigns:

- channel,
- variant,
- role,
- macro/micro stage,
- age group,
- difficulty condition.

Attack type is derived from channel and variant:

```text
email + fake -> phishing
sms + fake -> smishing
voice + fake -> vishing
any channel + real -> legitimate
```

Difficulty is assigned by the case-set design. It is not a new human label added after generation. The paper should state this clearly.

### Who labeled the difficulty band?

The difficulty band is engine-assigned from the macro/micro stage and the 120-case experimental design. It should be described as a rule-based design label. It is not an independently human-annotated difficulty label unless future expert annotation is added.

## 2. Four Generation Modes

### Mode 1: Prompt-Only

The prompt-only baseline uses the case controls and prompt engineering, without external retrieval and without ontology constraints.

Purpose:

- no-retrieval baseline,
- shows what the local LLM or fallback generator can do from prompt instructions alone,
- provides a lower-control comparison condition.

### Mode 2: Prompt+RAG

Prompt+RAG uses the same case controls plus retrieved examples from the RAG corpus.

Purpose:

- tests whether evidence examples improve grounded scenario generation,
- uses the same source corpus across retrieval-enabled methods,
- does not add ontology semantic constraints.

### Mode 3: Ontology+Prompt+RAG

Ontology+Prompt+RAG adds an ontology semantic packet to prompt+RAG.

Purpose:

- injects structured PSQ-SCO constraints,
- preserves selected templates, quality rules, and evidence requirements,
- tests whether ontology-guided semantic controls improve conformance.

### Mode 4: Ontology-Text+Prompt+RAG

Ontology-text RAG converts ontology graph structure into text documents and adds them to the RAG context. This follows the idea that graph structure can be converted into retrievable textual evidence for LLM prompting.

Purpose:

- tests ontology-as-retrieval-context rather than ontology-only packet control,
- supports graph-to-text and random-walk-style ontology descriptions,
- lets the LLM see ontology concepts, validation rules, templates, and evidence constraints as textual context.

Current interpretation:

The newest run shows strong grounding and ontology scope for ontology-text RAG, but lower required-concept precision/F1 than ontology+prompt+RAG. This means the method is semantically grounded, but the prompt/context balance may include extra or weakly matched concept terms. The result should be discussed as a design trade-off, not a failure.

## 5. Metric Definitions in Paper Language

### JSON validity

JSON validity is an average pass rate:

```text
1 = parseable JSON row with an inspectable scenario object
0 = malformed row or no inspectable scenario object
```

If all rows are valid JSON, the method mean is 1.0.

### Schema completeness

Schema completeness checks whether valid JSON rows contain the fields required for game execution and research auditability.

This is why a method can have:

```text
json_validity = 1.0
schema_completeness < 1.0
```

That means the output is parseable but incomplete.

### Required-concept precision/recall/F1

These metrics are not baseline-normalized against prompt-only. They compare generated content against required concepts derived from the case and ontology/control specification.

Prompt-only is not automatically 1.0 because prompt-only can miss required controls.

Paper wording:

```text
Required-concept precision, recall, and F1 are computed against the requested case specification and ontology-derived control concepts, not against prompt-only output. Therefore, prompt-only is a comparison condition rather than a gold standard.
```

### Grounding completeness

Grounding completeness checks whether the scenario can be traced to evidence and provenance:

- source ID,
- source title or dataset,
- evidence role,
- provenance record,
- retrieval mode,
- source record ID.

Paper wording:

```text
Grounding completeness is a provenance-oriented metric. It measures whether the generated scenario records enough source/evidence information for auditability, rather than whether the prose is persuasive.
```

### Ontology semantic scope

Ontology semantic scope is inspired by EL Embeddings, but it is not a full EL embedding model.

The paper by Kulmanov et al. addresses vector-space embeddings for EL++ theories that preserve TBox model semantics. PSQ-SCO uses this principle as a lightweight diagnostic: generated ABox-like scenario instances should remain within TBox-like ontology controls.

Paper wording:

```text
The ontology semantic-scope metric is inspired by the model-preservation motivation of EL Embeddings. It does not train a neural EL embedding model. Instead, it operationalizes the same principle at evaluation time by checking whether concrete generated scenarios preserve ontology-selected templates, validation rules, evidence grounding, source identifiers, case controls, and non-contradiction.
```

### Embedding diversity

Embedding diversity measures semantic variety across the 120 scenarios in a model/method condition:

```text
EmbeddingDiversity = 1 - mean_{i<j} cosine(E_i, E_j)
```

Higher values mean the scenario set is less semantically repetitive.

Available local fallback:

```text
embedding_backend = local_hashing_ngram
embedding_model = scenario_structure_hashing_v1_512d
```

Completed neural rerun:

```text
sentence-transformers/all-MiniLM-L6-v2
intfloat/multilingual-e5-small
sentence-transformers/LaBSE
```

The E5 run uses the recommended `passage:` prefix for scenario texts before embedding.

### Self-BLEU

Self-BLEU measures lexical redundancy:

```text
SelfBLEU = (1 / N) * sum_i BLEU(x_i, X_-i)
```

Lower Self-BLEU means less repetition. The completed rerun uses SacreBLEU sentence BLEU when installed. Self-BLEU is useful for detecting redundancy, but it should not be used alone because it does not measure scenario quality.

### Case-reference BERTScore

BERTScore measures contextual semantic similarity between a generated scenario and a reference text. In this project, the reference is not a human-written ideal scenario. It is an automatic case-reference built from the frozen 120-case specification:

- role,
- macro/micro stage,
- age group,
- channel,
- variant,
- expected attack type,
- difficulty condition,
- safe-response expectation,
- required cybersecurity and ontology/control concepts.

The evaluator exports:

```text
bertscore_scenario_alignment.csv
bertscore_method_summary.csv
```

Paper wording:

```text
BERTScore is reported as a case-reference semantic-alignment metric. Because the current study does not yet include human-written reference scenarios for all cases, the reference text is automatically constructed from the frozen case specification and required ontology/control concepts. The score therefore measures semantic adherence to the requested case, not final human expert acceptability.
```

This metric complements required-concept precision/recall/F1. Required-concept F1 is an explicit concept-coverage metric; BERTScore is a softer contextual similarity metric that can recognize paraphrased case-relevant wording.

## 6. Why the Weighted Score Is Not the Whole Evidence

The compact formula is:

```text
Overall Conformance = 0.20 JSON Validity
                    + 0.25 Control Adherence
                    + 0.25 Required-Concept F1
                    + 0.20 Grounding Completeness
                    + 0.10 (1 - Contradiction Rate)
```

The advisor's concern about coefficients is valid. The paper should not present this weighted score as a discovered law. It should present it as a transparent reporting index and then show each component metric separately.

Recommended wording:

```text
The weighted conformance score is used as a compact comparison index for paired method analysis. To avoid hiding metric-specific trade-offs, the paper reports all component metrics separately. The weights reflect the evaluation design priority that control adherence, required concept coverage, and grounding are central to deployable scenario generation, while JSON validity and contradiction checks function as basic execution and safety gates.
```

For stronger future work, the weights should be calibrated from:

- expert-labeled scenario acceptability,
- manual inspection labels,
- learner outcome data,
- normalized learning gain,
- or a multi-criteria decision process such as AHP.

## 10. TBox/ABox Explanation

A useful academic explanation:

```text
The PSQ-SCO ontology functions as a TBox-like structure that defines the allowed concept space: attack-channel categories, role and age suitability, stage progression, templates, validation rules, evidence sources, and safe-response constraints. Generated scenarios are ABox-like instances: concrete emails, SMS messages, calls, choices, feedback, and role contexts. The generation engine should not treat retrieved examples as the whole universe. It should use retrieved examples as evidence patterns while allowing diverse new ABox-like scenario instances that remain inside the ontology's TBox-defined scope.
```

This answers the concern:

```text
Right now it is like using the ABox as the universe, so it cannot go beyond that boundary.
```

The revised interpretation is:

```text
RAG examples provide evidence patterns. The ontology controls the semantic boundaries. The LLM can generate diverse instances as long as the generated instance preserves the ontology-defined controls.
```

## 11. Assumptions and Limitations

State these explicitly in the paper:

- The 120 cases are generated from deterministic design labels, not independent human labels.
- Difficulty bands are rule-assigned from stage and experimental design.
- Channel categories are treated as primary labels: phishing/email, smishing/SMS, vishing/voice. Real attacks can be multi-channel; multi-channel attacks are future work.
- The current ontology semantic-scope metric is diagnostic, not a formal EL embedding model.
- Some older condition files include fallback rows; pure LLM-performance claims require reruns with `--require-live-llm`.
- Automated metrics do not replace expert scenario review.

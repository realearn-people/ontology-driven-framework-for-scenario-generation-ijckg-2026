# Three-Layer PSQ-SCO Scenario Evaluation Engine: Technical Documentation

## 1. Purpose

This program evaluates generated PersonaShield Quest scenario content. It does not evaluate learner performance. The current evaluator is designed for the 120-case paper experiment comparing four generation modes across three local lightweight LLM conditions:

1. `prompt_only`
2. `prompt_rag`
3. `ontology_prompt_rag`
4. `ontology_text_rag`

The evaluator answers the advisor's methodological questions by making the dataset, matching design, retrieval corpus, metric definitions, timing, ontology validation, and manual-inspection workflow explicit.

The newest version also adds corpus-level semantic diversity and redundancy metrics. See:

```text
docs/SEMANTIC_DIVERSITY_AND_SELF_BLEU_METRICS.md
```

The newest version also adds case-reference BERTScore semantic alignment. See:

```text
docs/BERTSCORE_CASE_REFERENCE_METRIC.md
```

The complete neural-embedding rerun installed and used:

## 2. Three Evaluation Layers

The final structure uses exactly three evaluation layers.

### Layer 1: Ontology Validation

Layer 1 evaluates the PSQ-SCO ontology, not generated prose. It checks:

- OWL ontology inventory: class count, named individuals, object properties, datatype properties.
- Formal consistency through an imported HermiT report when available.
- Unsatisfiable class count.
- SPARQL ASK competency-question checks.
- Runtime mapping preservation: generated scenario records can be mapped back to ontology-relevant case controls.

The ontology file used by default is:

```text
ontology/ontology/personashield-psq-sco-v9.1.owl
```

The current completed run imported:

```text
ontology/outputs/v9_1/hermit-reasoner-report.json
```

This avoids reporting a "not run" ontology result when the completed formal reasoner output already exists for the same ontology.

### Layer 2: Scenario Validation

Layer 2 evaluates each generated scenario row. It checks whether the scenario is parseable, executable, aligned to the requested case, grounded, and internally consistent.

The scenario score is stored in:

```text
scenario_scores.csv
```

Main metrics:

- `json_validity`
- `schema_completeness`
- `control_adherence`
- `required_concept_precision`
- `required_concept_recall`
- `required_concept_f1`
- `grounding_completeness`
- `ontology_semantic_scope`
- `contradiction_rate`
- `overall_conformance`

### Layer 3: Method Comparison

Layer 3 compares generation methods on matched case IDs. It does not compare unrelated generated stories. The same 120 case specifications are used for every method and model. Therefore, paired comparisons answer:

```text
For the same requested role, stage, age group, channel, variant, and difficulty condition, which method produced the more conformant scenario?
```

Layer 3 writes:

- `method_summary.csv`
- `model_method_summary.csv`
- `model_method_matrix.csv`
- `paired_statistics.json`
- `matched_case_audit.csv`
- `timing_analysis.csv`
- `diversity_analysis.csv`
- `semantic_diversity.csv`
- `semantic_diversity_method_summary.csv`
- `bertscore_scenario_alignment.csv`
- `bertscore_method_summary.csv`

## 3. Why 120 Cases?

The 120 cases are a frozen matched design:

```text
30 base groups = 3 channels x 2 variants x 5 roles
90 anchor cases = 30 base groups x 3 difficulty anchors
30 balanced repetitions = 30 base groups x 1 extra case
Total = 90 + 30 = 120 cases
```

The 120 cases are not 120 random stories. They are controlled input specifications. The scenario generated by each method can differ in surface wording, but it must satisfy the same requested case slot.

## 4. Dataset and RAG Corpus

The evaluator now exports a dataset description to:

```text
dataset_description.json
dataset_sources.csv
```

The paper-facing report includes:

- source type,
- number of source files,
- raw document count,
- used document count after profile caps,
- source origin,
- preprocessing,
- chunking,
- embedding note,
- vector database,
- retrieval settings,
- and whether the same source corpus is used across conditions.

In this project, `prompt_rag`, `ontology_prompt_rag`, and `ontology_text_rag` use the same `PSQ_RAG_PROFILE=quality` retrieval corpus unless explicitly overridden. `prompt_only` is the no-retrieval baseline.

The current code uses ChromaDB PersistentClient when available:

```text
Vector database: ChromaDB PersistentClient
Vector space: cosine HNSW
Index path: genai_engine/chroma_db_quality
Embedding model: ChromaDB default embedding function, because rag_engine.py does not pass a custom embedding_function.
```

Chunking rule:

```text
One JSONL record becomes one retrieval document by concatenating available text, subject, body, messages, dialogue, and cue fields.
```

Preprocessing rule:

```text
Short text rows are skipped, exact lowercased text hashes are deduplicated, and quality-profile caps prevent very large public corpora from dominating retrieval.
```

## 5. Metric Definitions

### JSON Validity

`json_validity` is binary:

```text
1.0 = the row is parseable JSON and contains an inspectable scenario object
0.0 = malformed row or no inspectable scenario object
```

The mean JSON-validity score is therefore an average pass rate. It is not the same as schema completeness.

### Schema Completeness

`schema_completeness` measures whether the scenario contains required game-executable and evidence/provenance fields. A row can be valid JSON but still be incomplete as a deployable research artifact.

Required game fields include:

- `scenario_id`
- `channel`
- `variant`
- `game_choices`
- `correct_action`
- difficulty field
- red flag or safe-indicator field
- evidence/source/provenance field

### Control Adherence

`control_adherence` is the fraction of requested controls matched:

- role,
- age group,
- macro/micro stage,
- channel,
- variant,
- difficulty band,
- attack type,
- safe response behavior.

### Required-Concept Precision, Recall, and F1

These are standard information-retrieval/classification-style metrics applied to scenario content. They compare generated concepts with required case and ontology/control concepts.

They do not compare against prompt-only as a gold baseline. Therefore, prompt-only is not automatically 1.0.

Definitions:

```text
precision = matched generated required concepts / generated concept candidates
recall    = matched required concepts / required concepts
F1        = 2 x precision x recall / (precision + recall)
```

If a method adds many relevant and irrelevant terms, precision may fall. If it includes most required controls, recall may rise. F1 summarizes the balance.

### Grounding Completeness

`grounding_completeness` is a provenance/evidence pass rate. It checks:

- source ID,
- source title or dataset name,
- evidence role,
- provenance record,
- retrieval mode,
- source record ID.

This follows the RAG evaluation principle that generated output quality and retrieval-grounding quality should be inspected separately.

### Ontology Semantic Scope

`ontology_semantic_scope` is inspired by the EL Embeddings paper included by the user. That paper argues that ontology-aware embeddings should preserve model-theoretic TBox constraints of EL++ theories. This project does not train EL embeddings. Instead, it adds a lightweight diagnostic that asks whether an ABox-like generated scenario remains inside the ontology's TBox-like semantic controls.

The score checks:

- ontology packet or ontology text trace exists,
- selected scenario template evidence exists,
- validation-rule evidence exists,
- evidence-source grounding exists,
- source IDs are preserved,
- graph route or Graph-CoT style ontology trace exists,
- requested controls are satisfied,
- contradiction checks pass.

This is a scope-preservation metric, not a theorem prover and not a learned embedding model.

### Contradiction Rate

`contradiction_rate` is 1 when a scenario violates high-level consistency rules, such as:

- wrong attack type for the requested channel/variant,
- a real scenario containing malicious indicators,
- unsafe correct action,
- missing independent verification/reporting behavior for a fake attack.

Lower is better.

### Embedding Diversity

`embedding_diversity` checks whether scenarios are meaningfully different from one another. It is computed for each 120-scenario model/method condition:

```text
EmbeddingDiversity = 1 - mean_{i<j} cosine(E_i, E_j)
```

Higher is better. The default backend is a deterministic local scenario-structure hashing embedding (`scenario_structure_hashing_v1_512d`) so the evaluator can run without downloading neural embedding models. For final publication, rerun with a documented sentence/document embedding model if available.

### Self-BLEU

`self_bleu` checks redundancy. Each generated scenario is treated as a candidate and the remaining scenarios in the same condition are treated as references:

```text
SelfBLEU = (1 / N) * sum_i BLEU(x_i, X_-i)
```

Lower is better. The evaluator also reports `self_bleu_diversity = 1 - self_bleu`, where higher is better.

When installed, the evaluator uses SacreBLEU sentence BLEU for Self-BLEU. If SacreBLEU is unavailable, it falls back to an internal smoothed BLEU implementation.

### Case-Reference BERTScore

`bertscore_precision`, `bertscore_recall`, and `bertscore_f1` measure contextual semantic similarity between each generated scenario and an automatic reference built from the same frozen case specification.

The reference contains:

- role,
- macro/micro stage,
- age group,
- channel,
- variant,
- expected attack type,
- difficulty condition,
- safe-response expectation,
- required cybersecurity and ontology/control concepts.

This is a case-adherence proxy. It is not human-reference BERTScore because the project does not yet include human-written reference scenarios for all case/method/model outputs.

Output files:

```text
bertscore_scenario_alignment.csv
bertscore_method_summary.csv
```

Publication wording:

```text
BERTScore was used as a case-reference semantic-alignment metric. The reference was automatically assembled from the frozen case controls and required ontology/control concepts, so the score measures semantic adherence to the requested case rather than final expert acceptability.
```

### Overall Conformance

The compact reporting formula is:

```text
Overall Conformance = 0.20 JSON Validity
                    + 0.25 Control Adherence
                    + 0.25 Required-Concept F1
                    + 0.20 Grounding Completeness
                    + 0.10 (1 - Contradiction Rate)
```

This weighted score is a compact reporting index. The paper should report the separate metrics first, because they explain where the method improves and where it fails.

## 6. Timing Analysis

The evaluator now reports generation-time information in:

```text
timing_analysis.csv
```

Two timing sources are used:

1. Direct LLM timing telemetry, when saved in the generated row.
2. Observed interarrival time from generation timestamps, for older runs that did not save per-call timing.

Direct timing is preferred. Observed interarrival time is an approximation and should be reported as such.

## 7. Diversity and Repetition Analysis

The evaluator writes:

```text
diversity_analysis.csv
semantic_diversity.csv
semantic_diversity_method_summary.csv
```

This checks whether 120 outputs are simply repeated from limited inputs. It reports:

- unique scenario fingerprint count,
- unique fingerprint rate,
- unique title count,
- unique title rate,
- most common title,
- most common title frequency.
- embedding diversity,
- mean pairwise embedding cosine similarity,
- Self-BLEU,
- Self-BLEU diversity.

Automatic diversity metrics are not enough for final paper claims. The evaluator also exports a manual inspection sheet.

## 8. Manual Inspection Workflow

The evaluator writes:

```text
manual_inspection_sample.csv
```

This sheet is intentionally not pre-labeled. A human researcher should inspect the sampled outputs and fill:

- manual JSON usability,
- channel/variant fit,
- cybersecurity realism,
- pedagogical fit,
- grounding plausibility,
- repetition issue,
- acceptability,
- comments.

This directly answers the advisor's comment that some outputs should be randomly verified by a human.

## 9. Scenario Generation vs Question Generation

The evaluator treats scenario generation and question generation as separate stages.

Scenario generation creates the grounded event:

- channel message,
- sender/caller,
- role context,
- red flags or safe indicators,
- correct defensive action,
- feedback.

Question or choice generation should then use the scenario as grounding. This prevents the engine from treating a question as the whole scenario.

## 10. TBox/ABox Boundary

The ontology functions like a TBox:

- concept scope,
- attack/channel structure,
- role and stage suitability,
- validation rules,
- evidence requirements,
- safe-response constraints.

The generated scenarios are ABox-like instances:

- concrete email/SMS/voice cases,
- concrete choices,
- concrete feedback,
- concrete role context.

The engine should not use retrieved ABox examples as the whole universe. It should use examples as evidence patterns while allowing the LLM to generate diverse new instances that remain within the ontology's concept scope.

## 11. How to Run

From PowerShell:

```powershell
cd genai_engine
$PY = "python"

& $PY .\evaluate_three_layer.py `
  --paper-120-final `
  --out-dir output\three_layer_eval_3models_120cases_4modes_advisor_aligned
```

For complete neural diversity evaluation, install optional dependencies and cache models locally:

```powershell
cd genai_engine
$PY = "python"

& $PY -m pip install --target .\.codex_pydeps `
  sentence-transformers scikit-learn nltk sacrebleu

$env:PYTHONPATH = (Resolve-Path .\.codex_pydeps).Path
$env:HF_HOME = (Resolve-Path .\.hf_cache).Path
```

Run SBERT:

```powershell
& $PY .\evaluate_three_layer.py `
  --paper-120-final `
  --diversity-embedding-backend sentence_transformers `
  --diversity-embedding-model sentence-transformers/all-MiniLM-L6-v2 `
  --out-dir output\three_layer_eval_3models_120cases_4modes_sbert_complete
```

Run E5:

```powershell
& $PY .\evaluate_three_layer.py `
  --paper-120-final `
  --diversity-embedding-backend sentence_transformers `
  --diversity-embedding-model intfloat/multilingual-e5-small `
  --out-dir output\three_layer_eval_3models_120cases_4modes_e5_complete
```

Run LaBSE:

```powershell
& $PY .\evaluate_three_layer.py `
  --paper-120-final `
  --diversity-embedding-backend sentence_transformers `
  --diversity-embedding-model sentence-transformers/LaBSE `
```

Run case-reference BERTScore:

```powershell
& $PY .\evaluate_three_layer.py `
```

## 12. Important Reporting Caveat

Some older generation files contain fallback rows. The evaluator records this with:

- `used_live_llm_rows`
- `fallback_rows`
- `live_llm_rate`
- `fallback_rate`

If a condition has fallback rows, report it as an engine-output condition, not a pure live-LLM condition. For strict model-comparison claims, rerun that condition with `--require-live-llm`.
